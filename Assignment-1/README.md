# Assignment 1 — Mutex locks, sense-reversing barrier, concurrent counters

C++20 implementations of three synchronization primitives, with correctness tests and a performance study:

1. Mutex locks: TAS, TTAS (with and without exponential backoff) and MCS, compared with the library locks.
2. A sense-reversing barrier with several waiting strategies, compared with the library barriers.
3. Concurrent counters built on a lock, on compare-and-swap and on fetch-and-add.

The assignment statement is [`Assignment1_18092026.pdf`](Assignment1_18092026.pdf). Correctness is checked by stress tests, ThreadSanitizer and mutation testing. Part 4 of the assignment (a distributed version with MPI-3 RMA, optional) is not implemented. The report is written in Vietnamese.

Every number in the report comes from one pipeline, with no step done by hand:

```
build/bench_*  →  results/<host>/*.csv  →  report/figures/<host>/*.pdf + tables.tex  →  report/report.pdf
   (make)            (make bench)                   (make figures)                        (make report)
```

## Quick start

```sh
make check       # build, then every correctness check: tests, ThreadSanitizer, mutation testing
make full        # the whole workflow: check, measurement campaign, figures, report, zip
```

`make check` also saves the output of each check in `results/<host>/` (see [Running the measurement campaign](#running-the-measurement-campaign) for the host name). `make full` runs the steps one after another and stops at the first failure. The campaign takes about an hour and needs an idle machine (see [Running the measurement campaign](#running-the-measurement-campaign)); before it starts, the runner waits up to 10 minutes for the load left by the tests to fall. Figures and the report need matplotlib, numpy and XeLaTeX: with a virtual environment, run `make full PYTHON=.venv/bin/python` (see [Figures and report](#figures-and-report)).

## Requirements

- A C++20 compiler: Apple clang (macOS arm64), or g++ / clang++ (Linux x86-64 or arm64). `make`.
- Python 3 to run the measurement campaign. No extra package is needed.
- To draw the figures and build the report: `matplotlib`, `numpy`, and XeLaTeX (a full TeX Live with `latexmk`).
- OpenMP is optional. The OpenMP baselines are compiled only when the compiler accepts `-fopenmp`: g++ on Linux does; Apple clang needs `brew install libomp`. The benchmarks take their list of implementations from `build/bench_* list`, so a machine without OpenMP runs the same campaign without those baselines.

## Build and test

```sh
make             # build the tests and benchmarks into build/
make test        # run every correctness test
make tsan        # run the tests again under ThreadSanitizer, with smaller sizes
make mutation    # build deliberately broken variants and check that the tests catch each one
make check       # all four above, in order, saving the logs in results/<host>/
```

To use another compiler: `make CXX=g++-14`.

CMake builds the same programs (`cmake -S . -B cmake-build-release && cmake --build cmake-build-release && ctest --test-dir cmake-build-release`). Mutation testing, measurements, figures and the report are Make targets only.

## Running the measurement campaign

On each machine that should appear in the report:

1. Plug in the power, turn off power saving, and close other programs (browser, IDE, video calls, cloud sync).
2. `make check` builds everything, runs the correctness checks and saves their logs in `results/<host>/`.
3. `make bench-dry` prints the parameter grid and the estimated duration without measuring anything.
4. `make bench` runs the full campaign, about one hour on a 10-core laptop. Do not use the machine while it runs.
5. Keep the folder `results/<host>/` as it is. Do not edit any file in it.

The host name comes from the system hostname. To choose another one, pass the same name to every step: `make check HOST=my-machine` and `make bench HOST=my-machine` (or `python3 scripts/run_bench.py --host my-machine`).

`results/<host>/` contains:

| File | Contents |
|---|---|
| `lock.csv`, `barrier.csv`, `counter.csv` | One row per run: the columns of `pc::csv_header()` (`host, arch, os, compiler, ncpu, part, impl, threads, iters, outside_work, n, seconds, ops, ops_per_s, ok, load1, extra`) plus `rep, timestamp, wall_s` |
| `calibration.json` | The iteration counts chosen for this machine, fixed for the whole campaign |
| `machine.txt` | The machine description written by `scripts/machine_info.sh` |
| `sleep_latency.csv` | The real duration of `sleep_for`, `yield` and the spin-wait hint |
| `campaign.log` | Start and end time, load average, number of timeouts |
| `test.log`, `tsan.log`, `mutation.log` | The output of `make test`, `make tsan` and `make mutation`, written by `make check` |
| `mutation_logs/` | The log of every run of every mutant, copied from `build/` by `make check` |
| `lock_yield.csv` | Only after the optional `make bench-relax` |

Common situations:

| Situation | What to do |
|---|---|
| `load average is ..., above 7.0` | The machine is busy. Close programs and start again, or wait up to 10 minutes with `python3 scripts/run_bench.py --wait 10`. `--force` measures anyway, but numbers from a busy machine are not usable in the report |
| The campaign was interrupted (Ctrl-C, battery) | `python3 scripts/run_bench.py --resume` runs only the missing runs, with the same iteration counts |
| Measure again from scratch | `python3 scripts/run_bench.py --fresh`. The old data moves to `results/<host>/old-<time>/`; nothing is deleted |
| Measure only one part | `--part lock`, `--part barrier`, `--part counter` (repeatable); `--impl 'tas*,mcs'` selects implementations |
| Test the whole pipeline quickly (1–2 minutes) | `make quick`: a tiny grid with 2 repetitions, written to `build/quick-results/`, never to `results/` |
| Compare the ISB and YIELD spin-wait hints (AArch64 only, optional) | `make bench-relax` after `make bench` has finished |

## Figures and report

```sh
python3 -m venv .venv && .venv/bin/pip install matplotlib numpy     # once
make figures PYTHON=.venv/bin/python     # results/*/  →  report/figures/<host>/*.pdf, tables.tex
make report                              # report/report.pdf (XeLaTeX)
make zip                                 # assignment1.zip: sources, scripts, results/, report
```

`scripts/plot.py` reads every folder in `results/` and generates, for each machine:

| File in `report/figures/<host>/` | Contents |
|---|---|
| `lock_time.pdf`, `lock_time_short.pdf` | Run time against thread count, one panel per `OUTSIDE_WORK`, with the ideal lower bound; `_short` is for short critical sections |
| `lock_throughput.pdf` | Critical sections per second |
| `lock_slowdown.pdf`, `lock_slowdown_short.pdf` | Measured time divided by the ideal lower bound |
| `lock_cs_length.pdf` | Effect of `N`, the length of the critical section |
| `lock_backoff.pdf`, `lock_backoff_short.pdf` | Backoff variants against plain TAS and TTAS |
| `lock_fairness.pdf` | First thread to finish against last thread to finish |
| `lock_relax.pdf` | ISB against YIELD (only when `lock_yield.csv` exists) |
| `barrier_rate.pdf` | Barrier episodes per second |
| `counter_time.pdf`, `counter_variants.pdf`, `counter_cas_failures.pdf` | Counter run time, variants against the base version, failed CAS per increment |
| `tables.tex` | Every table and every figure caption, as LaTeX macros |

With results from two or more machines, `report/figures/cross/` also holds cross-machine figures. `report/figures/cross/tables.tex` always holds the table of machine configurations. Points are medians; error bars span the minimum to the maximum. A missing CSV file or implementation skips the corresponding figure with a message, not an error.

### Adding a machine to the report

1. Copy its `results/<host>/` folder into `results/`.
2. `make figures PYTHON=.venv/bin/python`
3. In `report/report.tex`, add the host name to `\providecommand{\Hosts}{...}` (comma-separated, no spaces) and add a line `\PCsetowner{<host>}{<name>}`.
4. `make report`

The machine table, the machine's figures and tables, and the cross-machine figures appear without further edits.

## Measurement rules

- One measuring process at a time. Do not run two benchmarks, or a benchmark and `make test`, on the same machine.
- The machine must be idle. `run_bench.py` does not start when the 1-minute load average is above 7 (change it with `--load-max`). It logs the load at the start and the end in `campaign.log`, and every row has a `load1` column. After the first minute, `load1` includes the campaign itself.
- Repetitions are the outer loop and configurations are interleaved. Each configuration runs 7 times. Within each repetition, the configurations of all three parts are shuffled with a fixed seed, so a slow drift in background load or temperature cannot favour one implementation.
- Iteration counts are fixed for the whole campaign (`calibration.json`). Locks use `I = W_N / max(threads, 1 + OUTSIDE_WORK)` so that every run takes about the same time. Barriers and counters calibrate `I` per configuration with one trial run. Because `I` differs between configurations, figures and tables compare time normalised to the same iteration count.
- A run that exceeds its time limit is data, not an error. It is recorded as a row with `ok=0, extra=timeout`, and the configuration is measured again with 100 times fewer iterations. After two timeouts it is skipped (`extra=timeout_skipped`). The queue lock (MCS) with more threads than cores starts with 100 times fewer iterations.
- Raw data is never filtered or edited. Only `run_bench.py` writes to `results/`. A run left out of the analysis needs a reason stated in the report.
- No number is copied by hand. Tables and captions are generated by `plot.py`; the text quotes numbers from those tables, and the derived numbers come from `scripts/report_numbers/`.
- Fake data never reaches `results/`. `fake_bench.py` prints `host=FAKE…`; `run_bench.py` refuses to write such rows to `results/`, `plot.py` refuses to draw them into `report/`, and `make zip` stops if it finds `results/FAKE*`.

## Changing the tooling

- The parameter grid is one block at the top of `scripts/run_bench.py` (`GRID`, `REPS`, `THREADS`, `TIMEOUT_S`, `REDUCED_ITERS`).
- Colours, markers and order of each implementation are in `FAMILY_STYLE` at the top of `scripts/plot.py`. An implementation keeps the same colour and marker in every figure.
- To test the pipeline without real benchmarks, writing outside the project:

  ```sh
  python3 scripts/run_bench.py --fake --quick --force --out /tmp/a1
  .venv/bin/python scripts/plot.py --results /tmp/a1 --figures /tmp/a1-figures
  ```
